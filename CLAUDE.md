# Nuzline: standing rules

Design: `docs/design.md`. Pipeline: `docs/process.md`.

- **Battle rules come from the decomp only** (`external/pokeplatinum`). Never state or build a rule from memory; cite file and line. For every rule read both the C (`src/battle`) and the battle scripts (`res/battle/scripts`): checks such as Shield Dust sit in scripts.
- **Game data comes from the ROM, then the calc repo, then the docs sheet** (`docs/kaizo/pipeline.md`). Fill a blank from the next source and keep the citation; nothing is "unknown" until all three are silent. Every real battle belongs to a split.
- **Doubles-ready code:** new engine and AI code follows section 5 of `docs/doubles-state-design.md`.
- **Build for the complete engine:** no tests, guards or special cases that only matter while coverage is partial. Model the missing mechanic instead.
- **Safety over speed:** a line's win chance outranks saving allowed resources.
- **Never write to any `backup` folder.** Never commit the user's ROMs or save files; copy them only into the git-ignored `.cache/`.
- **Pushing:** to `origin` only the managing session pushes, only `main`, after each merge that passed a fresh review agent. To the private remote `offsite` only `tools/ops/offsite.sh` pushes, run by the managing session. Work streams never push. Every merge into local `main` goes through a fresh review agent.
- **Batches:** a batch is 15-20 mechanic groups of one family (fewer only when the family is smaller). Send the family list to the managing session before starting a batch. Build, review and fix each batch by the pipeline in `docs/process.md` section 2. Per batch run the focused tests plus the four guards: `tests/prep/test_variants.py`, `tests/data/test_game_constants.py`, `tests/tools/test_backlog.py`, `tests/test_cli.py`. No stream starts a third batch while two of its batches are unmerged.
- **Where tests run:** on the rented test pod (`docs/process.md` section 5). A stream sends the managing session its tip and test-file list while the batch is in work and again for the final tip; failures are fixed before the review. An in-work pod run uses the default mark `not slow and not fullset` and lists only the tests of the files the batch touches plus the test files that name a changed symbol; at most one in-work run per batch before the merge candidate, unless the first failed. The `fullset` tests of the touched areas run on the merge-candidate tip; all of them run in the nightly and the post-wave run. `pytest --collect-only` loads the engine: it is an engine run and goes to the pod. No engine test runs on the owner's PC, not even one id: a quick check goes to the pod through the quick lane (`docs/process.md` section 5). Locally a stream runs only ROM-reading tests, tool tests that do not import the engine, table builds and ROM tools: one process at a time, and only after waiting for free RAM above 6 GB plus the run's weight (`tools/ops/day/pod/weights.txt`).
- **Merges (the lean gate):** a merge into `main` needs the review agent plus one run set per landing, on the merged tip (the train tip for a train, never per member; on a train tip, the test lists of (2) cover only the cross-member surface of `docs/process.md` section 2 (Merge train), each member's own green gate standing): (1) the four guards; (2) the touched areas only: the test files of the code the diff changes plus every test file that names a changed public symbol (grep), nothing by directory; (3) `tests/test_differential.py 1 A` unless the differential skip below applies; (4) the snapshot compare against the standing capture when engine source or table inputs changed, the expected parts named beforehand; (5) the `fullset` tests of the touched areas, green in the stream first; (6) locally, in parallel to the pod runs: the whole ROM-only set for an engine train. Target one to two pod-hours per train; the READY TO LAND message prints the list sizes. Several ready batches may go into one merge, as a merge train (`docs/process.md` section 2, Merge train). **Differential skip:** a merge run may leave out `tests/test_differential.py 1 A` when every path of `git diff --name-only main..<train tip>` is under `docs/`, `tools/ops/` or `tests/`, or is a `*.md` file, and none of them is `tests/test_differential.py`, a `conftest.py`, `pyproject.toml`, `uv.lock`, a file under `src/` or `data/`, or a test helper module that `tests/test_differential.py` imports; print the path list and the verdict in the READY TO LAND message. Anything else carries the differential. The four guards and the touched areas always run. Backstop: the slow tier on `main` after each merge wave (at most once a day) carries the differential.
- **After merging `main` (or, in a merge train, the previous stream's tip) into a branch:** rebuild the vanilla and Kaizo tables before any test and scan for names, enum members and table rows defined twice. Then send the tip with `-m fullset` on its pod list (the tests that go stale when coverage grows: full sets and counts, refusals of mechanics not modelled yet). The pod runs them; a stream runs a `fullset` test locally only when it skipped on the pod for missing inputs (`tools/ops/day/DAYBOX.md`, Collect). A `fullset` failure is fixed before the merge-gate review. In a merge train only the last tip sends the `fullset` run, for the touched areas (`docs/process.md` section 2, Merge train); earlier members stop after the rebuild and the scan. A new test of that kind carries the `fullset` marker.
- **Test tiers:** once a day on `main`: the nightly (fast tier `-m "not slow"`, `fullset`, soundness sweep), plus one post-wave run after the day's last landing (or 16:00): fast tier and `fullset`, correctly split, on pods already up. A red nightly or post-wave run is fixed before new batches start. The slow tier (`-m slow`) runs on `main`'s tip after each merge wave (the merges of one day), at most once a day; it carries the heavy randomized soundness tests (over-size tests move there at reduced size); a red slow tier is fixed before new batches start. Slow tests stay out of every other gate except `tests/test_differential.py` (a merge run carries it unless the differential skip applies), the nightly's `tests/test_damage_oracle.py 1000 A` line, and the files a batch lists with the `A` flag. Deep soundness sweeps run in the nightly only, plus one standard-size sweep on a train that changes `enumerate.py`, `outcome.py` or the laws code (the managing session's call); in-work tips get none. The full suite runs only when a split closes. A fast-tier test stays under 60 s and under 2 GB above one loaded step (about 6.3 GB), or it is marked `slow`. Randomized tests run with fixed seeds everywhere except the nightly, which sets `NUZLINE_HYPOTHESIS_PROFILE=explore`; a nightly failure's reproduce line (`@seed` / `reproduce_failure`) goes to the stream that owns the test.
- **Usage:** no idle turns: run tests inside the subagent that needs the result. The managing session keeps every session under 35% of its context window: it clears a stream at a commit point once the stream is past 30%. Models: Opus writes rule sheets from the decomp, reviews, merges and fixes review findings; Sonnet builds from rule sheets (`docs/process.md` section 2) and does mechanical jobs checked on the spot (local test runs inside a stream, table rebuilds, ledger and backlog edits); pod runs follow `docs/process.md` section 5.
- **Run for a successor:** `docs/process.md` section 9; decisions in `docs/decisions.md`.
- Project files live inside the project folder: scratch, worktrees, scripts and logs in the git-ignored `_scratch/`; nothing on C: or beside the project.
