# Nightly fast tier on a rented Runpod CPU pod (brief for an Opus general-purpose agent)

Approval: run the nightly on Runpod, uploading only the source at the tip and the built game tables (`docs/process.md` section 5). On its own pod at most $6 per run; on `ci-day-big` there is no daily limit. Nothing else is approved.

Project: `<repo>`. Run the fast tier (`-m "not slow"`) on the tip of local `main`. The tip must equal `origin/main`; if not, stop and report. Skip rule: among the `<scratch>/rent/out/nightly-*` folders whose `meta.env` `COMMIT` equals the tip, take the newest by the `yyyymmdd` in the folder name (a folder without a date in its name is older than any dated one). Do not run, and report "no merge since the last nightly", only when that folder's `results/agg.txt` ends with `RESULT: PASS`, or with `RESULT: FAIL (...)` whose only reason is `<n> failed/errors`. Any other reason (`run not finished`, crashed units, units killed three times, collection failures, bad rc, incomplete files), a failed setup, no `results/agg.txt`, or no such folder: run. Steps, scripts and the never-upload list: `tools/ops/day/DAYBOX.md`. Test list: `tools/ops/day/nightly_files.txt` (whole files, slowest first, one test file per process, cut into chunks; the last line queues the rest). The list's first line runs the damage oracle, `tests/test_damage_oracle.py`, whole and without a `-m` filter (about 2 minutes, under 1 GB); after the checkout `setup.sh` runs `npm ci --prefix tools/smogon_calc`, and the exec-pod body's `env` must hold `"NUZLINE_REQUIRE_NODE":"1"`, so a missing node fails the run instead of skipping. The `env` also holds `"NUZLINE_HYPOTHESIS_PROFILE":"explore"`: the nightly alone runs the randomized tests with random seeds (`tests/conftest.py`; each unit log's terminal summary shows `nuzline hypothesis profile: explore`, next to the compile-cache line). Node comes from DAYBOX.md bring-up step 6, required on every pod. Its result counts in the nightly result like any other file. Run name: `nightly-<yyyymmdd>-<short tip>`.

You are the one agent for this run (`docs/process.md` section 5, "Pod runs"): launch, one blocking `wait.sh` call (no polling turns), collect, delete the pod this run created, final report.

## Hard rules

- Upload only what DAYBOX.md "Never upload" allows. Read `pack.sh`'s listing before sending the exec-pod body.
- Never write to any folder named `backup`. Write scratch only under `<scratch>\rent\`. Do not modify the main checkout or any branch; never push.
- No personal details in pod names, env vars or requests to outside services. Transfer files only with `runpodctl send` / `receive`. Load the skills `runpod:runpod-mcp` and `runpod:runpod-pod-deploy` first.
- **Pod.** If `list-pods` shows `ci-day-big` running and exec `tail -1 /work/bootstrap.log` on it prints `BOOTSTRAP_OK`, run on it and create no pod; if its `tail -1 /work/node_apt.log` does not print `NODE_OK`, run DAYBOX.md bring-up step 6 there first. Otherwise bring up one pod with `<name>` = `ci-nightly` per DAYBOX.md: `cpu3g`, 32 vCPU / 128 GB, a data center with HIGH stock. When `<scratch>/rent/VOLUME_ID` exists and the volume's data center has HIGH stock, create it there with the network volume (DAYBOX.md bring-up step 2), and publish before deleting it (DAYBOX.md "Network volume", step 5). Re-read price and stock with `list-cpu-types` before creating. If `cpu3g` costs more than $1.28/h, use nothing dearer than $1.76/h (`cpu3m`) and shorten the limit so hours x rate stays under $6. You delete `ci-nightly` yourself no later than 4.5 hours after creation (at $1.28/h), collecting logs first; delete it at once on an unrecoverable failure. No scheduled prompt deletes it for you. Stop or delete only the pod this run created, or `ci-day-big` as "Run" step 4 says. Confirm every deletion with a fresh `list-pods` read.
- Memory: the shape's limits and `SPACING` as `docs/process.md` section 5 (Test pod, the one SPACING rule) gives them hold the pod under its limit; do not raise `GATE_GB`; pass the `MAXP` of the live runs on the pod (the shape's value, or the lowered one while the pod is throttled: `docs/process.md` section 5, Chunking, the MAXP rule).

## Run

1. Build or reuse the tables for the tip, pick or create the pod, run the pod check (DAYBOX.md "Send a run" step 3; on `PODCHECK MIXED` send anyway and state the line in the report), `MARK='not slow' bash tools/ops/day/pack.sh <tip> <tables> nightly-<yyyymmdd>-<short tip> tools/ops/day/nightly_files.txt` (`MARK='not slow'`: the whole fast tier; `pack.sh`'s default leaves out `fullset`), read the listing, send the exec-pod body with `"env":{"NUZLINE_REQUIRE_NODE":"1","NUZLINE_HYPOTHESIS_PROFILE":"explore"}` added, plus the pod shape's `GATE_GB` and `KILL_GB` on a 256 GB pod (`docs/process.md` section 5) and `MAXP` as Memory above gives it. Note the pod id, whether this run created it, creation time, hourly rate and (for `ci-nightly`) the deletion deadline.
2. Read the body's output by DAYBOX.md "Send a run" step 6 (`RECEIVE_FAILED` or `UNPACK_FAILED`: pack again under the run name with `-2` appended). Then at once, one background Bash call: `bash tools/ops/day/wait.sh <run> --timeout <hours left before the deadline>` (DAYBOX.md "Wait"). It returns when the run is over (exit 0 PASS, 1 FAIL; the results are already in `<scratch>/rent/out/<run>/results/`), at the timeout (exit 3) or on an error (exit 4). Do not poll while it runs. On exit 4 for a usage error (bad argument or run name), fix the call and run `wait.sh` once more; on `payload not delivered`, pack again under the run name with `-2` appended and go back to step 1's send; on any other exit 4 (lock held, missing codes, broken `results.tgz`, `collect.sh` failed), go to step 3.
3. On exit 3 or 4: one `status.sh`, then `agg.sh`, `fetch.sh` and `collect.sh` by hand for what exists.
4. Delete `ci-nightly` if this run created it. If the run was on `ci-day-big` and a fresh `status.sh` of this run prints exactly `other active runs: none` (no other run, no `<name>(beacon)` run whose results are still on offer, and no `pytest_outside_this_run`) and the snapshot guard (DAYBOX.md "Snapshot compare", step 8, the exact exec given there) prints `GUARD_END` with at most `FAILED` lines before it (no snapshot job receives, syncs, waits or runs), delete `ci-day-big` (DAYBOX.md "Delete"), clear `<scratch>/rent/POD_ID` and report its hours and cost; if another run is active, leave it up. Confirm every delete with `list-pods`.
5. Locally, one process at a time and only above the free-RAM floor in `CLAUDE.md` ("Where tests run"), run in the main checkout with `-m "not slow"` the tests that skipped on the pod for missing inputs (mainly `tests/tools/rom`, `tests/kaizo/test_extract_*`, `tests/saves`, `tests/test_user_save.py`).

## Soundness sweep (after the fast tier)

Budget: 30 processes (2 nodes x 15 seeds, `tools/ops/sweep/nodes.txt`) x about 20 min each, 5 at a time on one pod: about 2 h wall, about 12 GB per process (60 GB at P = 5), so about 2 pod-hours on `ci-day-big` (about 4 pod-hours when the pod must be kept up for it after the fast tier ends). It runs only on the day volume pods (`ci-day-big`, the pod with the network volume) and only when no gate run holds the pod: `podcheck_body.sh` shows no gate run and the claims are empty (`/work/.claims`). Otherwise skip it and say "sweep skipped: pod busy" in the report. It needs a `main` that has both nodes (`::test_mask_sound_with_a_trainer_item` comes with E2's `e2-laws-a`, merged before this sweep). It never creates a pod of its own. It starts a process only under the pod lock, while no gate-run claim exists, and while memory + the live gate units' reserve + 13 GB stays under the pod shape's `GATE_GB` (taken from the container limit; DAYBOX.md "Soundness sweep"). A gate run that arrives while it runs can still be delayed: the sweep's processes are not runner units, so the runner sees their memory (up to about 60 GB, growing over minutes) but holds no reserve for it, and starts fewer units until they end.

1. Seeds: `python -m tools.ops.sweep.seeds <yyyymmdd> > <scratch>/rent/sweep-<yyyymmdd>-<short tip>.jobs` (the jobs file is kept with the results; a failure is rerun from its line).
2. Pack the tip as a normal run, `sweep-<yyyymmdd>-<short tip>`, with a minimal list so that `setup.sh` builds the repo, venv and tables: one line, `tests/tools/test_sweep.py 1`. Send it as DAYBOX.md "Send a run" (the pod check first).
3. When `setup.log` ends `SETUP_END` and that one unit has finished: `bash tools/ops/day/sweep_body.sh <run> <jobs file>` from a checkout at `main`, and send the printed body at once; its output must end `SWEEP_STARTED`.
4. When `sweep_out/SWEEP_DONE` exists (the check exec of DAYBOX.md "Soundness sweep" step 4; first look after 100 min, then every 10 min), fetch: DAYBOX.md "Soundness sweep". Give up when the check shows neither `SWEEP_DONE` nor `DRIVER_ALIVE`, or `SWEEP_STOPPED`, or 3 h after the start: stop it if the driver is alive (the stop exec there), fetch what is there, run step 5 and report "sweep not finished" with the last lines of `sweep_out/driver.log`.
5. `python tools/ops/sweep/collect.py <scratch>/rent/out/<run>/sweep_out`: writes `sweep_failures.txt` next to the logs; its first line is the result.

A sweep failure never changes the nightly's own PASS/FAIL. The report gets its own line, the first line of `sweep_failures.txt`, plus the class list. Each class (CLASS KEY, seeds, `@reproduce_failure` line) goes to the stream that owns the masks of `tests/engine/test_enumerate.py` (E2 today). Delete the pod only by the nightly's own rule (Run step 4) after the sweep results are fetched.

## Report (short)

Tip hash; pod name, spec, data center, created and deleted times, hours x rate cost (for `ci-day-big`: the nightly's hours); setup time vs test time; totals passed/failed/skipped (pod plus local part); `agg.sh`'s RESULT line with every incomplete file, collection failure, crashed chunk and chunk killed three times; every failure with its one-line error and whether it also fails locally; every Hypothesis reproduce line of a failure (`@seed(...)`, `@reproduce_failure(...)`) quoted in full from the unit log, with its test id; units killed and requeued; peak memory and largest process; the 15 slowest tests; the count of tests over 60 s; the soundness sweep line (or why it was skipped); problems hit; anything not done or not verified.
