# DAYBOX: chunked pytest runs on the test pod

Rules (pod shape, limits, what may leave the PC, chunk sizes, memory limits, completeness, exec-pod limits, dead pods, never signalling PID 1): `docs/process.md` section 5. This file holds the steps.

Who handles a run: `docs/process.md` section 5, "Pod runs".

Paths: the PC-side scripts run from any checkout or worktree; `tools/ops/common.sh` resolves the main checkout from `git rev-parse --git-common-dir` (override with `NUZLINE_REPO`) and the scratch folder `<scratch>` = `<main checkout>/_scratch` (override with `NUZLINE_SCRATCH`). PC-side state lives in `<scratch>/rent/`: `bin/runpodctl-windows-amd64.exe` (override with `RUNPODCTL`; download it by hand from the runpodctl GitHub releases page, the same version as the pod's, v3.1.1, into `<scratch>/rent/bin/`), `home/` (runpodctl config), `POD_ID` (the current pod id; never commit it), `tables_<short>.tar.xz`, `out/<run>/`. Pod side: `/work/_bin` (runpodctl, bootstrap; `/work/_bin/new` while a bootstrap runs), `/work/<run>` (one folder per run, its scripts in `/work/<run>/bin`). Run names: `[a-z0-9_-]`, a stream prefix plus a label (`e2-m26`, `nightly-20261118-235f2f8`), each used once.

## Bring-up (once per pod, about 3 minutes)

1. MCP `list-cpu-types` (include availability, product POD, vcpuCount 32): `cpu3g` at about $1.28/h with a data center in stock (128 GB), or the memory-optimized 32 vCPU type from `list-cpu-types` (256 GB). Shapes and their limits (`GATE_GB`, `MAXP`, `KILL_GB`, `SNAP_GATE_GB`): `docs/process.md` section 5, Test pod; on a 256 GB pod pass them in every exec-pod body's `env` and run `snap.sh` with `SNAP_GATE_GB=176`. Read a running pod's shape with exec `{"command":["sh","-c","cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes"],"timeoutSeconds":25}` (cgroup v2, else v1: some rented hosts are v1) or the pod check's `limit` (Send a run step 3); which value means which limits: `docs/process.md` section 5, Test pod.
2. MCP `create-pod` with `<name>` = `ci-day-big` (test pod) or `ci-nightly` (own nightly pod): `{"name":"<name>","cloud":"SECURE","cpu":{"id":"<cpu3g, or the memory-optimized type>","vcpuCount":32},"dataCenterIds":["<in stock>"],"image":"ubuntu:24.04","args":"{\"entrypoint\":[\"/bin/bash\",\"-c\"],\"cmd\":[\"sleep infinity\"]}","disk":60}`. Write the id into `<scratch>/rent/POD_ID`. PID 1 is `sleep infinity`, which never reaps orphans: zombies pile up for the pod's life, and no script may count a zombie as alive (`runner.sh` and `status.sh` skip them).
3. exec-pod, retrying on 409 while the container starts: `{"command":["sh","-c","mkdir -p /work/_bin && cd /work/_bin && nohup sh -c 'apt-get update -qq && apt-get install -y -qq curl ca-certificates >/dev/null && curl -LsSf -o runpodctl https://github.com/runpod/runpodctl/releases/download/v3.1.1/runpodctl-linux-amd64 && echo \"ae0a2e5ff723c8fceb609e7120dfcaa4d681bf3015adc74141812a21f2bb9486  runpodctl\" | sha256sum -c - && chmod +x runpodctl && echo RPC_OK' > /work/rpc.log 2>&1 < /dev/null & sleep 20; tail -1 /work/rpc.log"],"timeoutSeconds":25}`. Poll `tail -1 /work/rpc.log` until `RPC_OK`; a checksum mismatch stops here.
4. PC: `bash tools/ops/day/push_bin.sh`, then send its exec-pod body. `bootstrap.sh` installs the apt tools, uv and Python 3.12, checks the runpodctl checksum again and clones the decomp. The body receives into a fresh `/work/_bin/new` and moves the script and its log into place only after `BOOTSTRAP_OK`; every bootstrap step skips what is installed. Repeat it on a pod that is already up only when `bootstrap.sh` changed since that pod's bring-up (a change to `tools/ops/day/pod` needs none: those scripts travel in every payload and pod-check body); it may then run also while runs are active, with two limits: never send it while an earlier bootstrap is still running (the body removes `/work/_bin/new`), and a runpodctl checksum mismatch deletes `/work/_bin/runpodctl`, after which no run can be received until a bootstrap succeeds.
5. Ready when exec `{"command":["sh","-c","tail -1 /work/_bin/new/bootstrap.log 2>/dev/null || tail -1 /work/bootstrap.log"],"timeoutSeconds":25}` prints `BOOTSTRAP_OK` (`/work/_bin/new` is removed after a success; a failure stays there with its log).
6. Required on every pod (the nightly runs the damage-oracle test): exec-pod `{"command":["sh","-c","DEBIAN_FRONTEND=noninteractive nohup sh -c 'apt-get install -y -qq nodejs npm && echo NODE_OK' > /work/node_apt.log 2>&1 < /dev/null &"],"timeoutSeconds":25}`. Poll `tail -1 /work/node_apt.log` until `NODE_OK` before sending a run; `setup.sh` runs `npm ci` in `tools/smogon_calc` only when `npm` is present.

## Send a run (PC, Git Bash)

1. Tables. `bash tools/ops/build_tables.sh <B>` for every commit `<B>`, then pass `<scratch>/rent/tables_<short B>.tar.xz`. It keys the build on its inputs (`tools/ops/table_key.py`: the modules the table tools import, tracked data, interpreter and packages, node, decomp, symbols map, local inputs by content) and reuses `<scratch>/rent/tables/tables_k<key16>.tar.xz` when that key was built before: then it ends `BUILD_OK <path> (reused ...)` without a build and without the free-RAM need of Snapshot compare step 1. Never pick an archive of another commit by hand.
2. Test list, one line per entry, slowest first: `<test file, folder or node id> <ids per chunk> [A] [<GB>G]`. `A` drops the `-m` filter (slow tests included). `<GB>G` (for example `tests/search/test_stage_b_budget.py 1 A 85G`) raises the expected peak of every unit cut from the line to at least that many GB of 10^9 bytes; each unit weighs the larger of it and its heaviest id in `tools/ops/day/pod/weights.txt` (measured peaks of heavy tests and files, each citing its run; `UNMEASURED_FILE_GB` 20 for an id the table lacks, room for a file no run measured; every file any run measured is listed, at least 4 GB, and every test that passed alone in a 1-id chunk at least 4 GB under its file's line; per-test lines are measured in 1-id chunks only, and a multi-id chunk weighs the max over its ids). Give `<GB>G` for a new test or file expected over 20 GB that the table lacks.

   Refresh `weights.txt` after a nightly (managing session, PC): `python tools/ops/day/weights_from_agg.py tools/ops/day/pod/weights.txt <scratch>/rent/out/*/results/agg.txt > <scratch>/weights.new 2> <scratch>/weights.warn`, then read `<scratch>/weights.warn`. Move the new table into place (`mv <scratch>/weights.new tools/ops/day/pod/weights.txt`) and commit it only when that file has no `WARNING:` line. Resolve each warning first, then generate again: `rc 137 lower bound ...` (a kernel kill; the line already takes the bound, the real peak may be higher: add a hand-kept line above the marker at a weight that covers it, or rerun the file); `lower than before ...` (check that the lower peak is real, not a shorter run of the file; if not, keep the old value as a hand-kept line); `no longer measured, dropped ...` (pass the `agg.txt` that measured the file, or confirm the file is gone); `killed three times ...` and `hand-kept ids peaked ...` (raise or add the hand-kept line); `hand-kept line <GB> GB above its test's own peak ...` (delete the hand-kept line, so the test gets its generated line; when that peak is not the test's real cost, for example it skipped on the pod, add the word `keep` after the line's run name instead). The script keeps the hand-kept lines above its marker and regenerates one line per measured file (largest unit across the runs, or a larger rc 137 lower bound, at least 4 GB, run name), then one line per test that passed alone in a 1-id unit (rc 0, its log ends `1 passed`; of several, the largest peak) at least `PER_TEST_MARGIN_GB` (4) under its file's line (ids with a space or `#` get none). `per-test line lower than before ...`: check that the unit really ran the test (not a smaller case of it); if not, add the old weight as a hand-kept line.
   Hand-kept lines (per test, above the marker) are for tests of a file whose peaks differ widely, mostly the slow tier; a unit whose ids all have a hand-kept line does not count toward its file's generated line. Every line without `A` runs with `-m "not slow and not fullset"` (the per-tip run), or with `-m "<expr>"` when the list is packed as `MARK='<expr>' bash tools/ops/day/pack.sh ...` (`MARK` replaces the default; it is written into the payload's `meta.env`). The nightly packs with `MARK='not slow'` (the whole fast tier, `fullset` included) and its exec-pod body's `env` carries `"NUZLINE_HYPOTHESIS_PROFILE":"explore"` (random Hypothesis seeds; every other run uses the fixed-seed `gate` profile, `tests/conftest.py`); the `fullset` tests of a tip run only in its merge-candidate run (Merge candidate below). One run has one mark: a list that needs two different marks is two runs. A folder is cut per test file; an id already queued by an earlier line is skipped, so a last line `tests 40` queues the rest. The slow tier (`docs/process.md` section 3) packs with `MARK='slow'` and the one-line list `tests 8`: `setup.sh` collects `tests` with `-m slow` and cuts each file's slow ids into chunks of 8. Slow tests run in no other list except `tests/test_differential.py 1 A`, which every merge run carries, the nightly's `tests/test_damage_oracle.py 1000 A`, and the lines a batch flags `A` (`docs/process.md` section 3). Nightly list: `tools/ops/day/nightly_files.txt`.
3. Pod check, before every pack (every `pack.sh` call, Merge candidate and nightly included): `bash tools/ops/day/podcheck_body.sh`, run from a checkout at `main` (the main checkout, as step 4; it refuses otherwise), prints an exec-pod body: the two scripts travel inside it base64-encoded, cut into argv items of at most 4000 characters (exec-pod refuses an item over 4096 and more than 256 items; `tools/ops/common.sh` `exec_body`); send it with exec-pod as printed. It writes HEAD's `gate.sh` and `podcheck.sh` to `/work/_podcheck/` and runs `podcheck.sh /work <POD_SCRIPTS> <POD_WEIGHTS>` of HEAD: one line per active run (`run <name> gate=<GATE_VERSION|old> scripts=<first 12 hex of POD_SCRIPTS|old> runner=alive|setup live=<chunks> pending=<chunks>`), `weights other=<runs>` when an active run has another `weights.txt` (other expected peaks under the same gate rules: not a mix, no action), `memory <GB> GB limit <GB> GB|max|none` (cgroup v2, else v1), one line per claim (`runner alive|not-runner|dead`), and last `PODCHECK OK` or `PODCHECK MIXED old=<runs|-> other=<runs|->`. `old`: runs packed before `GATE_VERSION` (no reserves, gate lock or claims); `other`: runs packed with other gate scripts (`*.sh`, `weights.py`) than this checkout's. On `PODCHECK OK` go on. On `PODCHECK MIXED` do not pack: report the line to the managing session, which either waits until those runs end or sends anyway and states the mix (`PODCHECK MIXED ...`) in that run's report. `limit` is the container limit (the shape: Test pod rule in `docs/process.md` section 5).
4. `bash tools/ops/day/pack.sh <commit> <tables.tar.xz> <run> <files.txt>`. It draws two fresh random beacon codes, `WATCH_F` and `WATCH_D`, into `meta.env` (kept in `<scratch>/rent/out/<run>/meta.env`, never printed). The pod scripts come from git at HEAD of the checkout that runs `pack.sh`, not from `<commit>`: run `pack.sh` from a checkout at `main` (the main checkout) for every commit. It refuses while `tools/ops/day/pod` has uncommitted changes and while HEAD's `tools/ops/day/pod` differs from local `main`'s (`PACK_OFF_MAIN_POD=1` overrides, only for a road test of an ops branch, whose report states it). It writes `GATE_VERSION` (2), `POD_SCRIPTS` (sha256 over the packed `*.sh` and `weights.py`) and `POD_WEIGHTS` (sha256 of `weights.txt`) into `meta.env` (`setup.sh` copies them to `/work/<run>/gate.env` for step 3), checks every list line against the format of step 2, lists the payload, refuses forbidden files and any table entry outside `TABLE_ALLOW` or inside `TABLE_DENY` (`tools/ops/common.sh`), starts the send detached and prints the exec-pod body.
5. Send the printed body with exec-pod at once (the PC send waits for this receive). It receives into `/work/<run>`, starts `bin/notify.sh` (see Wait), runs `bin/setup.sh` (checkout, tables, env, collect, cut units) and starts `bin/runner.sh`. A failed receive or unpack ends `setup.log` with `RECEIVE_FAILED` or `UNPACK_FAILED`; then no `notify.sh` runs. A setup that fails after it has started its own error trap ends `setup.log` with `SETUP_FAILED`; one that fails earlier (`meta.env`) or is killed leaves no such line. The test is `status.sh`: `setup=gone` with `runner=none` (no `runner.pid`) is a failed run, with or without `SETUP_FAILED`.
6. Read the body's output (the last lines of `setup.log` after 15 s). `RECEIVE_FAILED` or `UNPACK_FAILED`: do not start `wait.sh`; pack again under a new run name and send that body. Neither those nor any `+` trace line of `setup.sh` (the receive still running): send exec `{"command":["sh","-c","tail -3 /work/<run>/setup.log"],"timeoutSeconds":25}` once; on `RECEIVE_FAILED` or `UNPACK_FAILED` there, as above. Otherwise, at once, as one background Bash call: `bash tools/ops/day/wait.sh <run>` (see Wait). No status polls.

Runner knobs go in that exec-pod body's `"env":{...}` (the body's `env` field; setup, runner and units inherit it; a variable set on the PC does not reach the pod): `GATE_GB` (start a chunk only while container memory + the reserve + the chunk's own expected peak stay under it; the reserve covers each live chunk's gap (expected peak minus current RSS, where positive) on the pod, all runs: every gap of a chunk weighing `RESERVE_FULL_GB` or more, and the `RESERVE_TOP` largest gaps of the lighter chunks, at least `RESERVE_PCT` % of their weight sum minus their RSS sum; with no live chunk on the pod: memory under it and memory + expected peak under `KILL_GB`, `docs/process.md` section 5, Chunking; default 88), `RESERVE_TOP` (light gaps reserved at once, default 2), `RESERVE_FULL_GB` (a chunk weighing this much or more keeps its whole gap reserved, default 40), `RESERVE_PCT` (the light reserve is at least this % of the light chunks' weight sum minus their RSS sum, default 75; the three `RESERVE_` knobs are whole numbers, any other value stops the runner with `ERROR: <knob> '<value>' is not a whole number`), `MAXP` (each runner compares its own `MAXP` with the pod-wide count of live chunks, all runs; default 10; every run gets the `MAXP` of the live runs on its pod, the shape's value or the lowered one while the pod is throttled: a run with a lower `MAXP` reserves nothing and stalls the other runs once per chunk through its claims; to throttle a pod restart every live runner with the lower value, Housekeeping step 4, and to end the throttle restart every live runner with the shape's value; `docs/process.md` section 5, Chunking, the MAXP rule), `DEFAULT_WEIGHT_GB` (expected peak of a live chunk without an `out/<unit>.w`, a run packed before weights; default 12, the 90th percentile of 7183 measured units, since those runs are mostly fast-tier chunks of measured files; not the 20 GB `weights.py` `UNMEASURED_FILE_GB` that a new run's never-measured file gets), `IDLE_WAIT_S` (an idle pod's wait for memory no chunk holds before starting a chunk that would pass `KILL_GB`, default 300), `RUNNER_LOCK` (the pod-wide lock file around each gate check and start, default `/work/.runner.lock`), `CLAIM_S` (s a head chunk is held before it claims the pod: skip-ahead stops, and other runs start only a chunk that fits beside the claimed one, logged `(claim-fit)`; default 120), `CLAIMS` (claim folder, default `/work/.claims`), `CLAIM_MAX_S` (a claim whose pid is alive but runs no `runner*.sh`, a reused pid, is deleted once older than this, logged `claim-expired` in the deleting runner's `runner.log`; a dead runner's claim is deleted at once, logged `claim-dead <name> pid <pid> age <s> s` in the deleting runner's `runner.log`; a live runner's claim never expires by time, it ends when that runner starts the claimed chunk or dies; default 3600), `UNIT_MAX_S` (a chunk running longer is killed: rc 96, listed in `out/timedout.txt`, a failure in `agg.sh`; the longest measured chunk wall is 10080 s, on uncontended pods; default 21600), `WORK` (the folder whose runs the pod-wide gate counts, default `/work`; tests only), `RUNMAXP` (chunks at once of this run, default `MAXP`; the way to give one run a smaller share: a runner at its `RUNMAXP` live chunks skips the gate, so it writes no claim and stalls no other run), `SPACING` (s between starts; the value and when to pass it: `docs/process.md` section 5, Test pod, the one SPACING rule), `KILL_GB` (default 118), `DUR` (pytest `--durations`, default 40), `COLLECTP` (collection jobs at once, default 4), `WATCH_HOURS` (how long `notify.sh` keeps offering its beacons, default 24), `WARMUP` (the node id the warm-up runs, default `tests/engine/test_step_basic.py::test_miss_deals_no_damage`; `none` skips it), `WARMUP_S` (warm-up time limit, default 900), `NUZLINE_TEST_COMPILE_CACHE` (default `/work/_jaxcache/jax-tests`), `NUZLINE_HYPOTHESIS_PROFILE` (`explore` for the nightly only; unset: `gate`). `MARK` is the exception: it is set on the PC for `pack.sh` (step 2) and read from `meta.env`, which overrides an exec-pod `MARK`. Pass the shape's limits and `SPACING` as `docs/process.md` section 5 (Test pod) gives them; every other knob stays at its default unless the managing session says otherwise. `setup.sh` records every knob the body set in `/work/<run>/run.env` (Housekeeping, Restart a runner). Compile cache: every unit of every run on the pod uses `NUZLINE_TEST_COMPILE_CACHE=/work/_jaxcache/jax-tests` (`unit.sh`); `tests/conftest.py` keeps XLA's compiled programs in `/work/_jaxcache/jax-tests/<16-hex hash of the jax and jaxlib versions>`, keyed by program, so a later run on the pod loads every program its commit leaves unchanged. Only that folder is pod-wide: the other caches (the trace exports, the CLI's `jax/` folders, each pruned to one code version) stay in the run's `repo/.cache`, so runs of other commits never prune each other's. JAX writes an entry with a plain file write (`LRUCache.put`), so a unit or warm-up killed while writing (memory kill, warm-up time limit) can leave a truncated entry that stays for the pod's life. Checked locally (jax 0.12.0.1, entries cut to half size): the entry is a compressed stream, so a read fails in Python decompression (`Error -5 while decompressing data: incomplete or truncated stream`), JAX warns `Error reading persistent compilation cache entry` (`jax/_src/compiler.py:823-826`), compiles cold and returns the right result; no crash. JAX does not replace the bad entry: every later process that needs that program warns and compiles cold again. When that warning shows in unit logs, delete `/work/_jaxcache/jax-tests` while no run is active on the pod. Warm-up: when the run has a `tests/engine` unit, `runner.sh` first runs `WARMUP` alone (`out/warmup/`, never a test result), so step is compiled once before the units start; `agg.sh` prints its rc, wall and CPU-s, and the units' CPU-s. Each unit's log ends with `tests/conftest.py`'s line `compile cache: <hits> hits, <writes> writes; highest peak during a test with a hit ..., with cold compiles only ...`; `agg.sh` lists it per unit (`compile cache per unit`), the hit-peak column of the memtable. After every JAX cache clear `conftest.py` calls glibc `malloc_trim(0)`. Threads: no thread limit is set. A probe on the 32 vCPU pod (run `e1-p2-cold`, 40ad9e0) measured `--xla_cpu_multi_thread_eigen=false` at 216 CPU-s / 117 s against 215 / 115 with no setting, still up to 29 running threads, and `taskset` refused by the container (`failed to set affinity: Invalid argument`); the probe and the setting were removed. The kill check runs once per runner loop (every 10 to 30 s), so the container can pass `KILL_GB` by a few GB before a chunk is killed.

One run per stream: a stream has at most one in-work run on the pod; a newer tip goes only after it is back, with the list `docs/process.md` section 5 ("One in-work run per stream") gives.

Restarts: `notify.sh` counts a run as dead only on two dead reads of `status.sh` 20 s apart (`runner=gone` without `DONE=y`). A runner restart whose runner is dead for less than 20 s (Housekeeping step 4: kill, 2 s, start) never shows on two reads: the beacon stays and `wait.sh` keeps waiting for the real end. A runner dead for 20 s or more ends the beacon: `notify.sh` offers the unfinished results as the run's end and `wait.sh` returns a false "run over". Set every knob in the exec-pod body at dispatch; a restart that cannot be avoided follows Housekeeping, Restart a runner.

Memory gate, known limits (one line each):
- Old runs: a live chunk of a run packed before weights has no `out/<unit>.w` and counts `DEFAULT_WEIGHT_GB` (12 GB); that run's own runner gates on memory and `MAXP` only, reserves nothing for any chunk and takes no `RUNNER_LOCK`, so it can start a chunk on the same reading as a new runner.
- Process groups: the weights are the largest single process's max RSS (`/usr/bin/time`), while the gate sums a chunk's whole process group; a test that spawns large subprocesses can be underweighted.
- Queued ids: a later list line cannot raise the weight of an id an earlier line already queued (the id runs in the earlier line's chunk); put the weight on the first line that queues it.
- Old-script runners ignore claims and reserves: a chunk of a new-script run can wait as long as old-script runs keep the pod full (road test: `mem 137 + reserve 77` already over `GATE_GB` 176 at `MAXP` 18). Do not send a new-script run to a pod that old-script runs keep full; stop or finish those first. Send a run step 3 (`PODCHECK MIXED`) finds them.
- Memory files: every pod script reads container memory through `gate.sh` `cgmem`: cgroup v2 (`/sys/fs/cgroup/memory.current`, `memory.max`, `memory.peak`), else cgroup v1 (`/sys/fs/cgroup/memory/memory.usage_in_bytes`, `memory.limit_in_bytes`, `memory.max_usage_in_bytes`). With neither, `setup.sh` fails (`SETUP_FAILED`), `runner.sh` stops with `ERROR: no cgroup memory file`, and a snapshot `run.sh` ends `times.txt` with `GATE_NO_CGROUP_MEMORY`.
- Warm-up: the warm-up process is not a chunk; no reserve is held for it.
- Light chunks: chunks under `RESERVE_FULL_GB` are reserved at `RESERVE_PCT` % of their weight (or their two largest gaps); light chunks that all peak at once can still pass `KILL_GB`, and the kill check requeues the newest.
- Stale run files: a `run/<unit>` file (the pid of the chunk's `setsid bash unit.sh`, its process group id once `setsid` has run) is counted only while that pid or a member of its group is alive and not a zombie (the pid covers the moment before `setsid`); a reused process group id would count as a live chunk until that run's runner clears the file.

## Road test (after any change to `tools/ops/day/pod`, before its merge)

On an empty test pod, from the ops branch's worktree with `PACK_OFF_MAIN_POD=1` (stated in the report). Each line passes or the merge waits:
1. Pod check: `podcheck_body.sh`'s body goes through exec-pod once, as printed, and ends `PODCHECK OK`.
2. Two runs at once, one with `tests/search/test_stage_b_budget.py 1 A 85G`: both end `DONE`, `runner.log` shows reserves and the gate lock at work, `agg.sh` passes.
3. A deliberate timeout: a one-line run with `"UNIT_MAX_S":"60"` in the body's `env` and a chunk longer than 60 s: that chunk gets rc 96, is in `out/timedout.txt`, and `agg.sh` fails it.
4. An expired claim of a dead runner: while a run holds a claim (`/work/.claims/<run>.<unit>`), kill that run's `runner.sh`; the next gate check of another new-script runner deletes the claim (a dead pid goes at once) and starts its chunks.
5. A cgroup v1 host, when one is rented: the pod check prints a number for `memory`, and a run starts.
6. Stop with a prefix pair: two runs live whose names are a prefix pair (for example `rt-a` and `rt-a2`); stop `rt-a` with `stop_body.sh rt-a` (Housekeeping step 2). The output ends `STOP_OK rt-a`, `/work/rt-a/STOPPED` exists, `rt-a2` keeps starting units (its `runner.log`) and its claims in `/work/.claims/rt-a2.*` survive.
7. Restart from `run.env`: restart one live runner by Housekeeping step 4 with one knob changed (for example `SPACING`): the new `runner.log` start lines show the changed knob taking effect (start gaps), and `tr '\0' '\n' < /proc/$(cat /work/<run>/runner.pid)/environ` shows every other knob of `run.env` unchanged.
8. Record in the road test's report: `cat /proc/sys/kernel/pid_max` on the pod, and whether a dead runner stays a zombie: `ps -o pid,stat -p $(cat /work/<run>/runner.pid)` after a run has ended (`Z`, or no line).

What the first road test (256 GB pod, limits `GATE_GB` 176 / `KILL_GB` 236) learned:
- Two 85 GB units (`tests/search/test_stage_b_budget.py 1 A 85G`) run together only while the rest of the container is under about 4 GB: 85 + 85 + memory must stay under `GATE_GB` 176 for the second to start, so any other chunk, page cache or snapshot job holds it (`hold` lines in `runner.log`) until it ends.
- Dead runners stay zombies (`ps` stat `Z`: PID 1, `sleep infinity`, never reaps them) and `pid_max` is 4194304: a zombie keeps its pid, so a dead runner's pid is not reused while the pod lives; `pidlive` and `podgate` still skip zombies, and `stop.sh`'s ownership check still guards the pids of processes that were reaped.

## Merge candidate (the `fullset` run)

Trigger: a stream message with the line `MERGE CANDIDATE <tip> fullset`, or a stream's request to run its tip with `-m fullset` on its pod list (`CLAUDE.md`, "After merging `main`"; `docs/process.md` section 2, step 7). Nothing else starts a `fullset` run. The managing session does not dispatch the merge-gate review of a tip that sent either trigger until `fullset_done.sh <tip> <list>` exits 0 for it.

1. Skip check: `bash tools/ops/day/fullset_done.sh <tip> <the stream's pod list>`. `FULLSET DONE <run>` (exit 0): a collected run of that commit with `MARK="fullset"` whose list held every entry of this one passed; do not run it again. `FULLSET NOT DONE` (exit 1): run it. Exit 2: a bad commit or list.
2. One run agent, right after the tip's targeted run and on the same pod (same commit: its programs load from the pod's compile cache): `MARK='fullset' bash tools/ops/day/pack.sh <tip> <tables> <stream>-fs-<short tip> <the stream's pod list>`, the same tables as the targeted run, preceded by the pod check (Send a run step 3; every pack is, also right after the targeted run), then Send a run steps 5-6 and Wait. Like every pack, run from a checkout at `main`. Drop the `A` from the list's lines first (an `A` line runs whole, slow tests included); a file without `fullset` tests collects nothing (`collect_rc=5`) and is not a failure.
3. A `fullset` failure goes back to the stream before the merge-gate review.
4. A merged `main` tip that differs from every stream tip with a passed `fullset` run (a merge of several batches, or a merge commit) has had no `fullset` check: its merge-gate run (`CLAUDE.md`, Merges; Send a run steps 3-6, pod check first) packs with `MARK='not slow'` instead of the default, so it runs the `fullset` tests too. A merge train's last tip merged `--no-ff` (`docs/process.md` section 2, Merge train) counts as checked when `git diff <last tip> <merge commit>` prints nothing; its `fullset` check is the last tip's own `MARK='fullset'` run (steps 1-3), and its targeted run uses the default mark.

## Snapshot compare

Rules, pass rule and the runners while a job runs (new runs keep the pod's `MAXP`; the memory gate and `SNAP_GATE_GB` protect the job): `docs/process.md` section 5. Script: `tools/ops/day/snap.sh` (PC, Git Bash; its header lists every check). Pod folders, short = the 7-char sha: `/work/snapmain-<short main>` (capture of a `main` tip; its `snap/` is what compares read), `/work/snapcmp-<stream>-<short tip>` (compare of a merge candidate), `/work/snap2-<short tip>` (re-capture, step 5). Each holds `repo/`, a `git archive` checkout without `.git`. No beacon: these are not pack.sh runs, and `status.sh` does not list them. A capture is never sent back to a pod; one lost with a pod is re-made on the next pod.

1. Tables: `bash tools/ops/build_tables.sh <B>` (Send a run step 1; a reuse ends `(reused ...)` and needs none of the following). A build needs more than 6 GB of free RAM (PowerShell: `(Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1MB`; other sessions' local tests take it for minutes: re-check every 3 minutes), one build at a time, and has succeeded only when its output ends with `BUILD_OK <path>` (the log holds many lines with the word error). The archive is named by the 8-character short sha (`tables_<8 chars>.tar.xz`); pod folders use 7 characters.
2. Memory gate: `snap.sh` writes `SNAP_GATE_GB` (default 88) into `run.sh`, which starts the job only while container memory is under it. Pass the shape's `SNAP_GATE_GB` (`docs/process.md` section 5, Test pod: 88, or 176 on a 256 GB pod).
3. Commands (PC, any checkout). Each refuses a name that exists under `<scratch>/rent/out/`, refuses forbidden files, writes `<scratch>/rent/out/<name>/body.json`, starts the send (`send.log` ends with `SEND_RC=<n>`) and prints the exec-pod body. Send that body with exec-pod at once. `--dry-run` runs every check and writes `run.sh` and `body.json` without sending; delete its folder afterwards.
   - Capture of a pushed `main` tip: `bash tools/ops/day/snap.sh capture <main sha> <tables>` (folder `snapmain-<short>`). About 90 minutes.
   - Compare of a merge candidate: `bash tools/ops/day/snap.sh compare <tip> <tables> /work/snapmain-<short main>/snap snapcmp-<stream>-<short tip> [--allow-new a,b,c]`. `<short main>` is the `main` tip the branch contains (`git merge-base <tip> main`). Leave out `--allow-new` when the stream's list is empty. The candidate's own `tools/snap_compare.py` compares. About 85 minutes.
   - Fetch logs or capture files: exec `{"command":["sh","-c","cd /work/<name> && tar -czf fetch.tgz times.txt *.log <more paths> || exit 1; nohup /work/_bin/runpodctl send fetch.tgz > fetch.log 2>&1 < /dev/null & sleep 10; grep -o 'code is: [^ ]*' /work/<name>/fetch.log"],"timeoutSeconds":25}` (the tar runs in the foreground, only the send in the background; no code: exec the grep once more), then PC `bash tools/ops/day/snap.sh fetch <name> <code>`: it lists the tarball first, refuses a `..` or absolute path, and unpacks into `<scratch>/rent/out/<name>/fetch-<epoch>/`.
4. Body output: `PREP_OK` is ready. An empty `prep.log` (the receive still running): exec `tail -3 /work/<name>/prep.log` once more. `RECEIVE_FAILED` or `UNPACK_FAILED`: run `snap.sh` again under a new name. `DECOMP_MISSING`: the pod has no `/work/_decomp/<decomp sha>`; send any pack.sh run first (its `setup.sh` creates it), then run `snap.sh` again under a new name.
5. Re-capture: when compare refuses the capture as written by an older `snap_compare` (another `format`), capture that `main` tip with the candidate's script: `bash tools/ops/day/snap.sh capture <main sha> <tables> snap2-<short tip> --tool <tip>`, then compare against `/work/snap2-<short tip>/snap`.
6. Finished: exec `{"command":["sh","-c","tail -3 /work/<name>/times.txt"],"timeoutSeconds":25}` once after the time above, again only while it does not end with `ALL_DONE`. A capture passes with `CAPTURE_RC=0` then `ALL_DONE`. A compare ends `COMPARE_RC=<n>` then `ALL_DONE`; `0` is `compare: ok`. Fetch `compare.log` (step 3) and send it to the stream; pass rule: `docs/process.md` section 5, "Snapshot pass rule". Failed: no `ALL_DONE` and no live `/work/<name>/run.sh` process (step 8 prints `FAILED /work/<name>`); `SYNC_RC=<n>` other than 0 means `uv sync` failed and the job stopped there. Fetch `capture.log` or `compare.log` and `sync.log` (step 3).
7. Keep and delete: the newest two `snapmain-*` folders stay. Remove an older capture folder only when the guard (step 8) prints no `runpodctl receive` line, every `run.sh` or `snap_compare` line belongs to a folder with a `RUNNING` line, and no `RUNNING` line's `reads=` names that folder. Delete a `snapcmp-*` or `snap2-*` folder once its result is sent.
8. Snapshot guard (exact exec): `{"command":["sh","-c","pgrep -af '[s]nap_compare|/work/[a-z0-9_-]*/run[.]sh|[r]unpodctl receive'; for t in /work/*/times.txt; do [ -f \"$t\" ] || continue; d=${t%/times.txt}; grep -q ALL_DONE \"$t\" && continue; if pgrep -f \"$d/run[.]sh\" >/dev/null; then echo \"RUNNING $d reads=$(cat $d/reads 2>/dev/null)\"; else echo \"FAILED $d\"; fi; done; echo GUARD_END"],"timeoutSeconds":25}`. `pgrep` lines: a snapshot job receiving, unpacking (`runpodctl receive`), syncing, waiting at the gate (`run.sh`) or running (`snap_compare`); a pack.sh run's receive shows too. `RUNNING <folder> reads=<capture>`: an unfinished job and the capture it reads (empty for a capture). `FAILED <folder>`: no `ALL_DONE` and no live `run.sh`. The pod may be deleted only when the output is `GUARD_END` with at most `FAILED` lines before it.

## Wait

`bash tools/ops/day/wait.sh <run> [--until done|first-failure] [--timeout <hours>] [--every <s>]` (defaults: `done`, 8 h, 120 s; every receive fetches the relay list from GitHub, so keep `--every` at 120 s or more) blocks on the PC until the run is over, or with `first-failure` until its first failure, and needs no pod exec: the exec-pod body starts `bin/notify.sh`, which reads `status.sh` every 20 s and offers two beacons with `runpodctl send --code <code>`: `f` = `firstfail.txt` (the status text) under `WATCH_F` at the first failure (a `BAD` unit, `COLLECT FAILED`, a running unit with F/E marks, `SETUP_FAILED`, a dead run), `d` = `results.tgz` (`fetch.sh --pack`) under `WATCH_D` once the run is over (`DONE=y`, or a failed run as defined under Status, seen twice 20 s apart). Each beacon is offered until taken or `WATCH_HOURS` pass; `f` also stops once `d` is taken. runpodctl's croc fork (`cmd/transfer/croc.go`) puts a transfer in the relay room named by the code's first 3 characters, so the two codes start with 3 random letters that differ. A croc code ends in the relay index the sender picked, so `wait.sh` tries `runpodctl receive <code>-<i>` for every relay index each round, at most 30 s each (a wrong index answers `room not ready` in under a second). The sweep ends at `relay index <i> not found` (end of the list) or `could not get list of relays` (HTTP 429 included); any other answer, such as an unreachable relay, is logged and the sweep goes on to the next index. Each round it also reads the payload send's `send.log`: a send that ended with `SEND_RC=<non-zero>` (written by `pack.sh`) before any beacon was taken exits 4 (`payload not delivered`). A run whose `results/agg.txt` already has a `RESULT:` line is reported at once. On `d` it unpacks the results with `collect.sh <run> --local`. One `wait.sh` per run at a time (lock `watch/lock`; a second call exits 4).

Output: one line `WAIT: RUN OVER, RESULT: ...` | `WAIT: FIRST FAILURE, run still going` | `WAIT: TIMEOUT ...` | `WAIT: ERROR ...`, then the `agg.txt` summary (per-file table, collection failures, crashed or killed units, wall, peak, failures; the full report is `<scratch>/rent/out/<run>/results/agg.txt`) or the status text. Exit 0 = over and `RESULT: PASS`, 1 = over and `RESULT: FAIL`, 2 = first failure (call `wait.sh <run>` again for the end; the `f` beacon is offered once), 3 = timeout, 4 = usage, lock or transfer error (payload not delivered: pack again under a new run name; a broken `results.tgz` is kept as `watch/results.tgz.broken`; fetch the results by hand, Collect). On exit 3 check the run once with `status.sh`. The beacon log is `<scratch>/rent/out/<run>/watch/wait.log`; on the pod `/work/<run>/notify.log` and `notify/`.

## Status (by hand only)

For a timeout, a run without `WATCH_F`/`WATCH_D`, or a question the beacons do not answer. `{"command":["bash","/work/<run>/bin/status.sh","20"],"timeoutSeconds":25}`: setup log lines, the line `setup=alive|done|gone runner=alive|gone|starting|none DONE=y|n` (always printed, also before `queue.txt` exists), collection failures, the line `other active runs: ...`, units done/running/pending/killed/crashed, memory, running units with F/E marks, every failing unit (`BAD u_NNN`) with its FAILED/ERROR lines. The run is finished when it prints `DONE=y`. A failed run: `runner=gone` without `DONE=y` (the runner died), or `setup=gone` with `runner=none` (setup died before starting the runner). `runner=starting` means setup is still alive and the runner is not up yet; keep polling. `other active runs:` lists every other run under `/work/*/` or `/work/*/*/` whose setup or runner process (any `setup*.sh` or `runner*.sh`) is alive and not a zombie, every other run as `<name>(beacon)` while its `notify.sh` is alive and its results are not taken (no `notify/taken_d`), plus `pytest_outside_this_run=<n>` for live pytest processes whose working folder is outside this run; it prints `none` only when both are empty. A chunk killed at the memory limit is requeued at most twice; a third kill gives rc 98 and counts as a failure. The runner writes `DONE` only when every unit has a result: a unit left without one is requeued, and counts with its kills toward the same two requeues.

## Collect

`wait.sh` already collected a run that ended with exit 0 or 1. By hand (no beacon); `fetch.sh` without `--pack` also writes `notify/taken_d` and `notify/stop`, so the run stops showing as `(beacon)` and its `notify.sh` stops offering:

1. `{"command":["bash","/work/<run>/bin/agg.sh"],"timeoutSeconds":25}`: per-file totals with the completeness column, collection failures, crashed chunks, wall time, the container peak while the run ran (max of its `mem_mb.txt`) beside the container's lifetime peak (both include other runs), largest process, per chunk its peak RSS and wall time (single-test chunks show their own cost), the 15 slowest tests, the count over 60 s, every failure and skip, and `RESULT: PASS` or `RESULT: FAIL (<reasons>)`.
2. `{"command":["bash","/work/<run>/bin/fetch.sh"],"timeoutSeconds":25}` prints a code. PC: `bash tools/ops/day/collect.sh <run> <code>` unpacks into `<scratch>/rent/out/<run>/results/`.
3. Tests that need the ROM, saves, `.cache`, the PKCalc zip, the docs sheet or their extractions skip on the pod. A skip there is not a pass: run those tests locally, one process at a time (`CLAUDE.md`, "Where tests run"), in a worktree of the run's commit, never in the main checkout (its built tables may be of another commit). Git Bash, `<M>` = the main checkout, `<C>` = the run's commit, `<s8>` = its 8-character short sha, `<wt>` = `<M>/_scratch/<stream>/local_<s8>`:
   1. `git -C <M> worktree add --detach <wt> <C>`.
   2. Tables: `tar -xJf <M>/_scratch/rent/tables_<s8>.tar.xz -C <wt>` (the archive the pod run used; none: `bash tools/ops/build_tables.sh <C>` first).
   3. `cp <M>/data/local.toml <wt>/data/local.toml`; for a test that reads `.cache` (ROM copy, symbols map), copy the folder it reads from `<M>/.cache/` into `<wt>/.cache/` (copies only; never point the worktree at `<M>/.cache`).
   4. Decomp junction, as `build_tables.sh` makes it: `powershell.exe -NoProfile -Command "New-Item -ItemType Junction -Path '<wt>\external\pokeplatinum' -Target '<M>\external\pokeplatinum' | Out-Null"`.
   5. With more than 6 GB free RAM, one process: `cd <wt> && PYTHONPATH="$(pwd -W);$(pwd -W)/src" <M>/.venv/Scripts/python.exe -m pytest -p no:cacheprovider -q -m "<the run's MARK>" <the skipped ids>` (`-m` left out for an `A` line).
   6. Clean up: first `cmd //c rmdir "<wt>\external\pokeplatinum"` (removes the junction only; `git worktree remove` would delete through it into the decomp), check that `<wt>/external/pokeplatinum` is gone, then `git -C <M> worktree remove --force <wt>`.

## Housekeeping (managing session)

1. Pod disk: before each gate dispatch exec `{"command":["sh","-c","df -h /work"],"timeoutSeconds":25}` and delete finished run folders. Keep `_bin`, `_decomp`, `_jaxcache`, `_python`, `_uvcache`, the standing `main` capture and active runs. A failed run name is used up: resend under a new name.
2. Stop a run: message the agent that owns it first ("superseded, do not resend"). Then, from a checkout at `main`, `bash tools/ops/day/stop_body.sh <run>` and send the printed exec-pod body as printed (`stop.sh` travels in argv items of at most 4000 characters, as the pod check's body). It runs `tools/ops/day/pod/stop.sh <run>` on the pod (any run, old scripts included), which kills, each with its descendants: the pids in `setup.pid`, `runner.pid` and `notify.pid` (`setup.sh` and `notify.sh` run under relative paths, so no `/work/<run>` command-line pattern finds them, and a live `setup.sh` would start the runner again), every process group in `out/run/*` (the chunks), and every process whose working folder is in `/work/<run>` (the runner's memory-log loop, also when the runner is already dead). A pid from a pid file or `out/run/*` counts only when it belongs to the run (its working folder is in `/work/<run>`, or its command line names `/work/<run>/bin/`): `setup.sh` exits after starting the runner, so on a live run `setup.pid` names a dead pid the kernel may have given to another run's process; such a pid is skipped and printed (`skip <pid> <file>: not this run's`). Runs nested under `/work/<run>/` stop with it. TERM, then KILL for what is left; never PID 1. It deletes the run's claims and writes `/work/<run>/STOPPED`. Last line `STOP_OK <run>`; `STOP_LEFT <pids>`: send the body once more, then report the pids. A process of the run that changed its working folder outside the run (some tests `chdir` to a temp folder) is skipped and printed (`skip <pid> out/run/<unit>: not this run's`) when its runner is already dead: kill the printed pid by hand after checking its command line (exec `tr '\0' ' ' < /proc/<pid>/cmdline`). Check that the next run's `runner.log` shows starts. Ten minutes after any dispatch check that the unit count moves.
3. Spacing: `docs/process.md` section 5, Test pod (the one SPACING rule). Changing it, or any other knob, on a live run is a runner restart (step 4).
4. Restart a runner (a knob change on a live run): tell the run's agent first. The restart below leaves the runner dead for about 2 s, under the 20 s `notify.sh` needs to count a run dead (Restarts, above): the beacon stays and the agent's `wait.sh` goes on. If the runner was dead for 20 s or more (the restart exec failed or was sent late), the beacon has ended: `wait.sh` returns a false "run over"; the agent then polls `out/DONE` and collects by hand (Collect). The restart repeats every env variable of the original dispatch, as recorded in `/work/<run>/run.env` (written by `setup.sh`: `export NAME='<value>'`, POSIX single quotes that `sh` and `bash` read alike, for each knob the exec-pod body set, of `GATE_GB` `MAXP` `RUNMAXP` `SPACING` `KILL_GB` `DEFAULT_WEIGHT_GB` `IDLE_WAIT_S` `RUNNER_LOCK` `CLAIM_S` `CLAIMS` `CLAIM_MAX_S` `UNIT_MAX_S` `RESERVE_TOP` `RESERVE_FULL_GB` `RESERVE_PCT` `WORK` `DUR` `COLLECTP` `WATCH_HOURS` `WARMUP` `WARMUP_S` `NUZLINE_TEST_COMPILE_CACHE` `NUZLINE_HYPOTHESIS_PROFILE` `NUZLINE_REQUIRE_NODE` `CGROOT`; never the beacon codes). A run packed before `run.env` existed has none: write it from the live runner first, exec `{"command":["sh","-c","cd /work/<run> && tr '\\0' '\\n' < /proc/$(cat runner.pid)/environ | grep -E '^(GATE_GB|MAXP|RUNMAXP|SPACING|KILL_GB|DEFAULT_WEIGHT_GB|IDLE_WAIT_S|RUNNER_LOCK|CLAIM_S|CLAIMS|CLAIM_MAX_S|UNIT_MAX_S|RESERVE_TOP|RESERVE_FULL_GB|RESERVE_PCT|WORK|DUR|COLLECTP|WATCH_HOURS|WARMUP|WARMUP_S|NUZLINE_TEST_COMPILE_CACHE|NUZLINE_HYPOTHESIS_PROFILE|NUZLINE_REQUIRE_NODE|CGROOT)=' | sed 's/^/export /' > run.env && cat run.env"],"timeoutSeconds":25}` (values without spaces only; check the output against the dispatch). Then exec, changing only the knob that changes (after the `.`): `{"command":["sh","-c","cd /work/<run> && kill $(cat runner.pid); sleep 2; set -a; . ./run.env; SPACING=4; set +a; setsid nohup bash /work/<run>/bin/runner.sh >> runner.log 2>&1 < /dev/null & echo $! > /work/<run>/runner.pid; sleep 3; tail -2 /work/<run>/runner.log"],"timeoutSeconds":25}`. Kill `runner.pid` only, never `pkill -P` (the chunks are the runner's children and keep running); use the absolute script path (a relative path hides it from `pgrep -f`). Record the changed value in `run.env` too. The old runner's memory-log loop keeps logging until `DONE`: harmless duplicate lines in `mem_mb.txt`.
5. A stuck claim: when the pod check (Send a run step 3) shows a claim older than about an hour whose runner is `alive`, read that run's `runner.log` (exec `tail -20 /work/<run>/runner.log`). A live runner's claim never expires by time (`CLAIM_MAX_S` covers reused pids only), so a hung runner (no new log line for several minutes while it should be checking the gate every 10-30 s) or a stopped one (`ps -o stat= -p $(cat /work/<run>/runner.pid)` shows `T`) holds every other new-script run on the pod. Then stop that run (step 2) and tell its agent; a runner that is still logging hold lines is waiting for memory, not stuck: leave it.

## Delete

When nothing is queued and `status.sh` of the last run prints `DONE=y` (or shows a failed run as defined under Status) and exactly `other active runs: none` (any listed run, `(beacon)` included, or `pytest_outside_this_run` keeps the pod up), and the snapshot guard (Snapshot compare, step 8) prints `GUARD_END` with at most `FAILED` lines before it: collect every run, MCP `delete-pod`, confirm with `list-pods`, clear `POD_ID`, log the hours and cost. Never stop the pod instead: a stopped CPU pod loses `/work` and saves nothing.

## Never upload

Only the `git archive` of a commit and the tables `TABLE_ALLOW` lists travel. Never the ROM (`*.nds`), saves (`*.sav`, `*.dsv`), `.cache/`, the PKCalc zip or its extraction (`data/intermediate_kaizo/pkcalc/`), the docs sheet or its extraction (`data/intermediate_kaizo/docs/`), `data/local.toml`, any file from the Desktop, anything in a `backup` folder. Never add files to a payload by hand. One exception to pack.sh payloads: the snapshot payload = the `git archive` of the commit plus its `TABLE_ALLOW` tables (and, for a re-capture, `tools/snap_compare.py` from the `--tool` commit's archive), built only by `tools/ops/day/snap.sh` with its checks. Never push from the pod.
