# Golden traces from the emulator

A golden trace is one real battle that was played in DeSmuME against the US Platinum ROM
and recorded turn by turn from battle RAM. `tests/test_golden.py` replays each recorded
turn through `step`, using the recorded actions and the realized chance outcome. The
engine's result must then equal the next recorded turn on every field in
`tools.trace_to_state.COMPARED_FIELDS` (spec §7, "Golden traces").

The pipeline has three stages:

1. `tools/trace_battle.lua` runs inside DeSmuME and writes a **raw trace**. This is a
   JSON-lines file with one `turn` record at every turn boundary and one `hit` or
   `move_end` record for each move-execution event in between.
2. `uv run python -m tools.trace_to_state --trace <raw.jsonl> --out tests/golden/roark_01.json --party tests/fixtures/golden_party_roark_01.toml`
   bundles the raw records with the player's party and the trainer id. It then converts
   the bundle once, to check that it converts, and writes it out. The bundle holds
   extracted battle state only and never ROM bytes. It is the only trace file that is
   committed. Raw traces belong in `traces/`, which is git-ignored.
3. `trace_to_states(bundle, tables, names)` rebuilds the turn-0 state from the party and
   the trainer, overlays each recorded turn, and infers both actions and the `Outcome` of
   every turn. The golden test replays those turns.

The ROM, saves, save states and raw traces are never committed (`.gitignore`: `*.nds`,
`*.sav`, `*.dsv`, `*.ds[0-9]`, `traces/`).

**Status:** the script, converter and tests exist. The converter is tested on synthetic
traces generated by the JAX engine (`tests/test_trace_to_state.py`).
`tests/golden/roark_01.json` has **not been recorded yet**. Recording it needs the
user's ROM and save, and `tests/test_golden.py` skips until the file exists. Several RAM
offsets below are marked **VERIFY** and still need checking on the emulator. The first
recording session should start with the checks in "Verifying the addresses".

## The recorded battle: Roark, `roark_01`

- **Opponent:** Roark, the Oreburgh Gym Leader. The trainer is resolved the way
  `nuzline --trainer roark` resolves it: the first trainer named Roark whose class starts
  with "leader" (trainer 246 in the current tables). The converter builds his party with
  `build_trainer_party` and his bag with `Trainer.items`, which holds two Potions.
- **Player:** `tests/fixtures/golden_party_roark_01.toml`. It starts as a copy of the
  M1a sample party (`tests/fixtures/sample_party.toml`), in this order:

  | Slot | Pokemon | Level | Moves | Item | Ability |
  |---|---|---|---|---|---|
  | 0 | Monferno | 14 | Scratch, Leer, Ember, Mach Punch | none | Blaze |
  | 1 | Prinplup | 14 | Pound, Growl, Bubble, Water Sport | none | Torrent |
  | 2 | Grotle | 14 | Tackle, Withdraw, Absorb, Razor Leaf | Sitrus Berry | Overgrow |
  | 3 | Starly | 10 | Tackle, Growl, Quick Attack, Wing Attack | Oran Berry | Keen Eye |
  | 4 | Shinx | 13 | Tackle, Leer, Spark | none | Rivalry |
  | 5 | Budew | 10 | Absorb, Growth, Water Sport, Stun Spore | none | Natural Cure |

  Every Pokemon has a Hardy nature, IVs 20, EVs 0, is male and starts at full HP.

  A real save will not hold these exact Pokemon, because IVs, natures and EVs come from
  the user's own playthrough. Before recording, **edit the TOML to match the save
  exactly**: species, level, nature, IVs, EVs, moves in slot order, held item, ability
  and gender. The IVs and EVs can be read from the save with any Gen 4 save editor. The
  converter compares the TOML-built turn-0 state with the first recorded turn on
  species, level, max HP, moves and item, and raises `TraceMismatch` naming the first
  difference it finds. A wrong IV or EV usually shows up there as a max-HP difference.
  Other stat errors only show up later, as damage that fits no roll.
- **Fight rules for a usable trace:**
  - Lead with slot 0. Fight until Roark's last Pokemon faints.
  - **No player Pokemon may faint.** The engine treats a player faint as terminal
    (spec §3), so the converter stops the trace at the first player faint, and the turns
    after it are lost.
  - Use only moves and switches, never a bag item: the player's bag is not modelled.
    Roark's own Potion use is inferred and replayed (actions 10 to 13).
  - The golden test needs at least three turns: three turn boundaries plus the final
    `turn` record.

## Running DeSmuME with the script

1. Use DeSmuME 0.9.13 or later for Windows (x64). Its Lua runs on Lua 5.1 with the
   `bit` library, which the script needs. Install `lua51.dll` next to `DeSmuME.exe` if
   the Lua window reports that it is missing.
2. Load the US Platinum ROM (`CPUE`) and the prepared save. Walk to Roark. Make a save
   state just before talking to him, so that a failed take can be retried.
3. Edit the config block at the top of `tools/trace_battle.lua`:
   - `TRACE_PATH`: where the raw trace goes, for example
     `G:/.../traces/roark_01.jsonl`. DeSmuME's Lua window takes no arguments, so this
     global is set in the file.
   - `BATTLE_SYSTEM`: leave it `nil` on the first run. The script then finds the battle
     structures by itself once a battle starts ("Locating the battle structures").
4. Open Tools > Lua Scripting > New Lua Script Window, browse to `tools/trace_battle.lua`
   and click Run. Then talk to Roark. The Lua console prints `trace: located ...` when
   the battle starts and one `trace: turn N` line per turn boundary.
5. Play the fight. When the battle ends, the script writes a final `turn` record (the
   result screen) and prints `trace: battle over`. Click Stop.
6. Convert the trace and run the test:

   ```bash
   uv run python -m tools.trace_to_state --trace traces/roark_01.jsonl \
       --out tests/golden/roark_01.json --party tests/fixtures/golden_party_roark_01.toml
   uv run pytest tests/test_golden.py -v
   ```

   The converter prints one line per turn: the inferred actions, the rolls that fit
   each hit, and any fields on which the engine's best replay disagrees with the trace.
   A golden failure means that no replayed candidate matches the trace. Usually that is
   an engine discrepancy: fix it as the decomp says, and log it in
   `docs/discrepancies.md`. It can also be a chance field that the converter did not
   enumerate on that turn (see the inference rules below), so check that first.

## RAM layout

All offsets come from the decomp's struct definitions (`external/pokeplatinum`, pinned in
`docs/decomp_paths.md`). They were laid out by hand with the ARM EABI rules that the
DS compiler follows: natural alignment, 4-byte pointers and ints, and bitfields packed
into their declared unit. The decomp names some padding members by their offset, such
as `padding0060`, `padding310A`, `unread_2440` and `padding0026_06`. Every chain of
offsets below is pinned to one of those named offsets, so an error in one chain cannot
move another. No ROM-built `.sym`/`.xMAP` was available when these were derived. A
build of the decomp (`make`, which yields `build/pokeplatinum.us.xMAP`) does not help
here either, because the battle structures are heap-allocated: only their offsets are
static.

The `VERIFY` rows depend on assumptions that cannot be checked without the ROM. Each
says what it depends on, and "Verifying the addresses" below says how to check it.

### `BattleSystem` (`include/struct_defs/battle_system.h`), heap

| Field | Offset | Derivation |
|---|---|---|
| `battleCtx` | `0x30` | 11 pointers, then `u32 battleType` at `0x2C` |
| `parties[0]` (player), `parties[1]` (opponent) | `0x68`, `0x6C` | `battlers[4]` `0x34`, `maxBattlers` `0x44`, `trainerInfo[4]` `0x48`, `bag` `0x58`, `bagCursor` `0x5C`, `pokedex` `0x60`, `pcBoxes` `0x64` |
| `seedRandNext` (32-bit battle RNG state) | `0x2444` | `unread_2440` (u8) at `0x2440`, `overlayFlags` u8, `networkID` u16; the anchor is consistent with `padding_2474_1` at `0x2474` |

### `BattleContext` (`include/battle/battle_context.h`), heap, `BattleSystem.battleCtx`

| Field | Offset | Derivation |
|---|---|---|
| `command` | `0x08` | after `curCommandState[4]`, `nextCommandState[4]` |
| `attacker`, `defender` | `0x64`, `0x6C` | `padding0060` at `0x60` |
| `totalTurns` | `0x150` | **VERIFY**: forward from `0x60`. This assumes `enum NarcID` is 4 bytes (mwcc's default `-enum int`) and `BattleMessage` is `0x24` bytes |
| `fieldConditionsMask` | `0x180` | **VERIFY**: same chain as `totalTurns` |
| `damage` | `0x2144` | backward from `battleMons` (`0x2D40`); see below |
| `criticalMul` | `0x2150` | same chain |
| `moveStatusFlags` | `0x216C` | same chain |
| `selectedPartySlot[4]` (u8) | `0x219C` | same chain |
| `moveCur` | `0x3044` | `moveTemp` `0x3040`, see `battleMons` |
| `battleMons[4]` | `0x2D40`, stride `0xC0` | `moveTemp` sits at `0x3040`, counted back from `padding310A`. `battleMons` is `4 * 0xC0` before it. Then `battleScript[400]` int (`0x2700`), `ioBuffer[4][256]` (`0x2300`), `ioQueue[4][4][16]` (`0x2200`), `monSpeedValues` `0x21F0`, `monSpeedOrder` `0x21EC`, `battlerActionOrder` `0x21E8`, `battlerActions[4][4]` u32 `0x21A8`, `aiSwitchedPartySlot` `0x21A4`, `switchedPartySlot` `0x21A0`, `selectedPartySlot` `0x219C`, `clearVolatileStatus[4]` `0x218C`, three u32 `0x2180`-`0x2188`, four u8 `0x217C`, `sideEffect*Flags` `0x2170`-`0x2178`, `moveStatusFlags` `0x216C`, ... `criticalMul` `0x2150`, `criticalBoosts` `0x214C`, `hitDamage` `0x2148`, `damage` `0x2144` |

`command` values come from `enum BattleControlSequence`
(`include/battle/battle_controller_player.h`). The script uses three of them, and each
is checked against the enum's `UNUSED_nn` markers:

- `INIT_COMMAND_SELECTION = 4`: the turn boundary. `COMMAND_SELECTION_INPUT = 5` also
  counts when no record has been written for the current `totalTurns` yet, for a run
  that located the structures after `INIT` had already passed.
- `UPDATE_HP = 27`: a move's damage is about to be applied. `damage` holds minus the
  uncapped damage (`BattleControllerPlayer_UpdateHP`,
  `battle_controller_player.c:3341`).
- `MOVE_END = 39` and `RESULT = 41`: the end of a move, and the battle result.

`BattleContext_Main` (`battle_controller_player.c:194`) runs one command per call. The
script polls `command` once per frame, so it relies on one call per frame (**VERIFY**):
every command it watches must be visible for at least one frame boundary.

### `BattleMon` (`include/battle/battle_mon.h`), size `0xC0`

| Field | Offset | Notes |
|---|---|---|
| `species` | `0x00` | u16 |
| `moves[4]` | `0x0C` | u16 |
| `statBoosts[8]` | `0x18` | s8, 6 = neutral, in the decomp's stat order HP, Atk, Def, Spe, SpA, SpD, Acc, Eva (`generated/battle_stats.txt`) |
| `ppCur[4]` | `0x2C` | u8; `padding0028_0B` anchors the preceding word |
| `level` | `0x34` | u8 |
| `curHP` | `0x4C` | s32 |
| `maxHP` | `0x50` | u32 |
| `status` | `0x6C` | u32 `MON_CONDITION_*` (`include/constants/battle/condition.h`) |
| `heldItem` | `0x78` | u16; `padding007A` anchors it |

The bitfield block `MoveEffectsData` is two u32 words, as `padding0004_1F` confirms. It
ends the struct at `0xC0`.

### `Party` (`include/party.h`) and `Pokemon` (`include/struct_defs/pokemon.h`)

`Party`: `capacity` `0x00`, `currentCount` `0x04`, `pokemon[6]` from `0x08` with stride
`0xEC`. A `Pokemon` is `BoxPokemon` (`0x88`) followed by `PartyPokemon`.

- `personality` `0x00`, flags `0x04` (bit 0 `partyDecrypted`, bit 1 `boxDecrypted`),
  `checksum` `0x06`, then four `0x20`-byte data blocks from `0x08`. The blocks are
  encrypted with `checksum` as the seed: each halfword is XORed with
  `LCRNG_NextFrom(&seed)`, which is `seed = seed * 1103515245 + 24691`, returning
  `seed >> 16` (`math_util.c:217`). Their order is `BoxPokemon_GetDataBlock`'s table,
  indexed by `(personality & 0x3E000) >> 13` (`pokemon.c:4861`).
- Block A: `species` `0x00`, `heldItem` `0x02`. Block B: `moves[4]` `0x00`,
  `moveCurrentPPs[4]` `0x08`.
- `PartyPokemon`, encrypted with `personality` as the seed: `status` `0x88`, `level`
  `0x8C`, `hp` `0x8E`, `maxHP` `0x90`.

The script reads the active battler of each side from its `BattleMon`, which holds the
live values. It reads the other party members from the decrypted `Party`.
`selectedPartySlot[battler]` indexes that `Party` (**VERIFY**: the battle reorders its
display order through `partyOrder`, not the `Party` itself).

### Locating the battle structures

`BattleSystem` and `BattleContext` live on the heap. With `BATTLE_SYSTEM = nil`, the
script scans main RAM (`0x02000000`-`0x023FFFFF`) on every frame for a `BattleMon` that
matches the player's lead. That is a word-aligned address where `species` equals
`LOCATE_SPECIES` (set in the config to the lead's species id, 391 for Monferno),
`level` equals `LOCATE_LEVEL`, and `curHP <= maxHP <= 999`. From such a match it takes
`BattleContext = match - 0x2D40`. It then scans for a word holding that address with
`BattleContext` at `+0x30`, which gives `BattleSystem`, and prints both. The scan stops
at the first match. It can take a second when the battle starts.

Once the scan has printed `BattleSystem`, put that address into `BATTLE_SYSTEM`. Later
runs from the same save state then skip the scan, because heap layout is deterministic
for a given save state.

### Verifying the addresses

On the first run, check each of these in DeSmuME's RAM viewer (Tools > View Memory),
starting from the printed `BattleContext`:

1. `totalTurns` (`+0x150`) reads 0 at the first command menu and goes up by 1 per turn.
   If it does not, search the area around `0x150` for that counter. Then update
   `CTX.totalTurns` and `CTX.fieldConditionsMask` by the same shift, because they share
   one chain.
2. `fieldConditionsMask` (`+0x180`) reads 0 in Roark's fight, which has no weather.
3. At the `UPDATE_HP` frame of a damaging move, `damage` (`+0x2144`) is minus the HP
   the defender then loses (unless the hit is a KO).
4. `selectedPartySlot[1]` (`+0x219D`) becomes 1 when Roark sends out Onix.
5. The party decode matches the summary screen for every benched Pokemon: species,
   level, HP and moves.

If any offset is wrong, fix the `CTX`/`MON`/`SYS` config table at the top of
`tools/trace_battle.lua` and this table together.

## Raw trace format

The raw trace is JSON lines. All ids are the decomp's own: species, move, item. Sides are
battlers: 0 is the player and 1 is the opponent.

```json
{"kind": "turn", "turn": 0, "command": 4, "rng": 123456789, "field": 0,
 "sides": [{"active": 0, "stages": [6,6,6,6,6,6,6,6],
            "party": [{"species": 391, "level": 14, "hp": 41, "max_hp": 41, "status": 0,
                       "moves": [10, 43, 52, 183], "pp": [35, 30, 25, 30], "item": 0}, ...]},
           {...}]}
{"kind": "hit", "turn": 0, "attacker": 0, "defender": 1, "move": 52, "damage": 7, "crit": 0,
 "active": [0, 0], "hp": [41, 30], "status": [0, 0], "stages": [[6,...], [6,...]]}
{"kind": "move_end", "turn": 0, "attacker": 1, "move": 33, "flags": 1}
```

- `turn` is written at each `INIT_COMMAND_SELECTION` (or `COMMAND_SELECTION_INPUT`,
  see above), and once more at `RESULT` (the last record; `"command": 41`). `stages` is the active battler's `statBoosts` in decomp
  order. `field` is `fieldConditionsMask`. `rng` is `seedRandNext`, which the converter
  does not use yet and keeps for a later RNG cross-check.
- `hit` is written at each `UPDATE_HP` with a non-zero `damage`. `damage` is the positive
  uncapped damage, `crit` is `criticalMul > 1`, and `active`, `hp`, `status` and
  `stages` are both battlers' values at that moment (before the HP drop). `crit` may be
  `null` when `criticalMul` cannot be trusted; the converter then tries both.
- `move_end` is written at each `MOVE_END`. `flags` is `moveStatusFlags`, where bit 0,
  `MOVE_STATUS_MISSED`, marks a miss.

## What the converter infers, and how

For each turn, `tools/trace_to_state.py` works out the following:

- **Actions.** A move slot is the slot whose PP dropped. A switch is an active slot that
  changed while the old active mon is still alive. When the side did not act (it
  fainted first, flinched, or was fully paralyzed), every legal move slot and, for
  Roark, every usable bag slot is a candidate, and the replay below picks among them.
- **Hit, crit, roll.** Each `hit` record of a side sets `hit = 1` and `crit` for that
  hit index, and a `move_end` with `MISSED` sets `hit = 0`. The roll is matched against
  `damage_for_roll` (the engine's `damage_table`) on the **hit-time state**: the turn's
  start state with the record's `active`, `hp`, `status` and `stages` written over it.
  `power_mul` is 20 for Pursuit hitting a switching foe. When no roll fits, the
  converter raises `TraceMismatch`, which names the move, the damage and the engine's
  table. Rolls that give the same damage cannot be told apart by any trace, and every
  later field of the turn is the same whichever is used, so the converter records all
  of them (`Turn.roll_candidates`) and uses the lowest. A hit whose `crit` is `null`
  raises `AmbiguousTrace`, carrying every candidate, when both a crit and a non-crit
  roll fit: whether a crit happened is an observable game event that the outcome must
  get right.
- **The other chance fields** are `speed_tie`, `end_speed_tie`, `full_para`, `thaw`,
  `secondary`, `contact_proc` (only when Static or Poison Point is in play) and
  `duration`. These are enumerated only where they can matter:
  - `speed_tie` when the start state's speeds are equal.
  - `end_speed_tie` when the speeds are equal in the start state, after the turn's
    switches, or after the switches with the next record's status and stages (a
    switch-in, a paralysis or a Speed change can create the tie).
  - `full_para` and `thaw` when the side's start-of-turn active mon is paralyzed or
    frozen at the start, in any `hit` record of the turn, or in the next record. A
    status inflicted earlier in the turn (Stun Spore, Spark, Static) can stop the
    slower mon on the same turn. A confusion self-hit is taken from a `hit` record whose
  attacker is also its defender, and its roll is matched against `confusion_damage`.
  Every candidate (actions times outcome fields) is replayed through `step`, followed
  by the opponent's replacement into the next record's active slot, and the candidate
  that matches the next record on the most `COMPARED_FIELDS` wins. Ties go to the first
  candidate. A best candidate that still disagrees is kept: the golden test then fails
  on that turn and names the field.

`COMPARED_FIELDS` is `species`, `level`, `hp`, `max_hp`, `status`, `status_counter`,
`item`, `moves`, `pp`, `active`, `stages` and `weather`. The dump does not fill the
other `BattleState` fields. Each turn takes them from the engine's own replay of the
previous turn, so they are carried forward and never checked:

- per slot: `form`, `stats` (only max HP is dumped), `types`, `ability`,
  `ability_slot`, `item_consumed`, `gender`, `friendship`, `ivs`
- volatiles: `confusion`, `leech_seed`, `substitute_hp`, `taunt`, `trapped`,
  `trap_move`, `flinched`, `choice_lock`, `last_move`, `protect_count`,
  `rollout_count`, `charge_turn`, `recharge`, `pursuit_target`, `water_sport`,
  `fake_out_turn`, `move_hit`
- side conditions: `spikes`, `toxic_spikes`, `stealth_rock`, `reflect`,
  `light_screen`, `safeguard`, `mist`, `lucky_chant`, `tailwind`, `wish_timer`,
  `wish_hp`, `future_timer`, `future_damage`, `trainer_items`, `trainer_item_count`
- field: `weather_timer`, `trick_room`, `gravity`, `mud_sport`
- bookkeeping: `turn` (the final record at `RESULT` comes before `totalTurns++`, so it
  would always differ by one), `over`, `winner`, `player_faints`, `ai_seen_moves`,
  `ai_ability_known`

Of these, `stealth_rock`, `trapped`/`trap_move` and `substitute_hp` are the most useful
to add next. They are in `sideConditionsMask`, `BattleMon.statusVolatile` and
`moveEffectsData` respectively, and their offsets are still to be laid out.

## Known limits

- A trace ends at the first player faint, which the engine treats as terminal.
- A side that used no PP and changed no compared field (fully paralyzed, or a
  Potion at full HP) is told apart only by `trainer_items`, which is not dumped. The
  converter tries move candidates before bag slots, so it reads such a turn as a move
  that did not happen.
- The player's bag items are not modelled. A trace that uses one fails to convert,
  because no action candidate fits.
- Multi-hit moves are read as one `hit` record per hit. They have not been exercised on
  a real trace.
- `selectedPartySlot` and the forward `BattleContext` chain are unverified (the
  **VERIFY** rows above).
