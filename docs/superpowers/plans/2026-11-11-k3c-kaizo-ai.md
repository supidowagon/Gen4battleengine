# K3c: the Kaizo trainer AI, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `uv run nuzline coverage --game kaizo --save <save> --trainer roark --cap 16` exit 0 on
both saves, with `Support: EXACT` for the fight and for the pool. To get there, transcribe Kaizo
Roark's trainer AI exactly: a per-game policy, `AI_FLAG_RISKY`, the script paths of his 20 distinct
moves, the per-game id lists, six-Pokemon switching, and a per-game AI outcome layout whose width
fits `WIDTH_CAP` (131072).

**Architecture:** The Kaizo AI script is the vanilla `gTrainerAITable` with one changed word.
`docs/kaizo/overlay14.md` §1-§3 (K3a) establish this: overlay14 is the same size, the only
script change is at 0x022249CC, and the other 31 changed functions are relocated calls. So the
Kaizo policy shares the vanilla transcription in `src/nuzline/ai/` and differs only where a
`AiLayout` (new, per game) says so:
- the Dry Skin compare;
- the RISKY flag;
- the transcribed effect set;
- the outcome layout.

The game's `Tables` carry a scalar `ai_policy`, and the Python entry points resolve the layout
from it before tracing. The vanilla layout and its code paths are untouched. The Kaizo layout
keys script-roll sites by move slot, so the exact distribution factors per slot (slots read
disjoint draws) instead of enumerating the flat product.

**Tech Stack:** Python 3.12 (uv), JAX, pytest, Hypothesis.

**Spec:** `docs/superpowers/specs/2026-11-07-kaizo-k3-design.md` §6, §8 (K3c), §9 item 1, §10.

**Sources (binding).** These are the decomp at `external/pokeplatinum`:
- `src/battle/trainer_ai/script.s` (written "script.s" below);
- `src/battle/trainer_ai/trainer_ai.c` ("trainer_ai.c");
- `src/battle/battle_lib.c` ("battle_lib.c");
- `src/battle/battle_controller_player.c` ("bcp.c").

Kaizo data comes from the Kaizo tables (`data/intermediate_kaizo/moves.json`, `species.json`).
Every AI rule below cites them. A task that finds the code saying otherwise follows the code and
reports it. Nothing comes from general Pokemon knowledge. The handover notes in
`kaizo-k3a/k3b2-handover.md` are inputs, not sources. This plan corrects three of their claims
(Plan-level rulings 3-5).

## Global Constraints

- The K3b1 and K3b2 Global Constraints still apply
  (`docs/superpowers/plans/2026-11-09-k3b2-draw-mechanics.md`):
  - both engines where a mechanic is touched;
  - an enum member lands in the same commit as its code;
  - a vanilla table change bumps `MANIFEST_VERSION`, rebuilds both games and commits the tracked
    manifest;
  - hard-coded decomp ids go in `game_constants`;
  - no ROM bytes or saves in commits, and saves are read in place;
  - never touch a `backup` folder;
  - commit trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`;
  - never push or merge.
- **Vanilla is frozen.** These stay exactly as they are:
  - the vanilla `AiOutcome` field shapes;
  - `ENUMERATION_WIDTH` (3840) and its import-time check against `MAX_ENUMERATED` (4096);
  - `_SITES`, `MOVE_EFFECTS` and the vanilla refusal set.

  Every vanilla AI distribution stays bit-identical. Spec §2 anti-goals and §6 require this.
- `WIDTH_CAP` (131072, `engine/enumerate.py:224`) and `MAX_ENUMERATED` are not changed. If the
  exact Kaizo AI is too slow for Stage B, stop and report measured numbers (spec §6).
- K3c adds no engine `Outcome` field and no `BattleState` field, so STATE.md does not change. If
  that turns out wrong, the K3b2 `fold_in(key, 16 + k)` rule applies.
- **The read-gating contract, applied to the AI.** The exact distribution may merge or drop a draw
  only where that draw cannot change the action. Each such gate gets two kinds of check:
  - a brute-force test against a *loose* enumeration in which every decomp `RandNext` read is its
    own independent draw (loose never reuses a gate);
  - mutation evidence: remove the gate and show a test fails.

  The gates in K3c:
  - script-roll sites read only on their path;
  - the one-scalar ability guess (Ruling 6);
  - the dropped speed-tie draw (Ruling 3);
  - per-slot factoring.

- Each task has three steps: the implementer, an independent review, then a fix round.
- **The full suite (about 80-100 minutes) runs once per task**, alongside the review, not before
  it. The controller starts it when the implementer reports.

### Task 3: The Kaizo AI outcome layout, factored distribution and loose oracle

**Files:** `ai/outcome.py`, `ai/policy.py`, `search/expand.py` (`ai_rows` resolves the layout and
passes it as a static key to `cached_export`), `search/playout.py`, `search/stage_b.py` (call sites
only), `docs/ai/kaizo_roark.md` §8 (draws). **Tests:** `tests/ai/test_kaizo_outcome.py` (new).

**Interfaces:**
- Consumes `AiLayout` and `layout_of` from Task 2.
- Produces:
  - `AiOutcome` with shapes per layout. For Kaizo, `script_rolls: int8[MOVES, KAIZO.slot_sites]`
    (slot, local site k). Vanilla stays `int8[MAX_SCRIPT_ROLLS]`.
  - `outcome.slot_site_table(tables, layout, move) -> (int32[slot_sites] N, ...)`: the N of each
    site of one move, from an effect-keyed table that Tasks 5 and 6 fill.
  - `sample_ai_outcome(key, tables, state, layout)` and `enumerate_ai_outcomes(..., layout)`.
  - `policy.ai_width(tables, state) -> int`.
  - `policy.ai_action_distribution_loose(tables, state)` (tests only).

**What the layout is.**
- One `ability_guess` scalar.
- Per-slot script-roll bits: `KAIZO.slot_sites` is the maximum site count of any transcribed
  effect. It is 8 for Selfdestruct: EvalAttack :6374 and :6383, Expert :1859, :1865, :1870,
  :1875, :1880, Risky :6530.
- `tiebreak` as today (`RandNext % 12`, trainer_ai.c:338).
- `switch_stop` over `KAIZO.switch_sites` (Task 7 sets it).

**The exact distribution, factored.**
- Each move slot's score depends only on its own sites and the guess. `TrainerAI_EvalMoves`
  scores slot by slot (trainer_ai.c:483-525), and `FlagMoveDamageScore` reads only deterministic
  damage (trainer_ai.c:1012-1062).
- Step 1: for each guess, run `_scores` once per local bit pattern p (2^slot_sites patterns, the
  same p applied to every slot).
- Step 2: build each slot's histogram over score values (`int32` 0-255).
- Step 3: get the pick distribution analytically. For a slot m with value v, sum over the subsets
  of the other candidate slots that tie at v, where every other slot is below v. The share is
  `TIEBREAK_P` of m's position in the tied list (trainer_ai.c:315-338).
- Step 4: add the switch first and the item next, as `_distribution` does (roark.md 2).
- Struggle and the locked slot are unchanged.

**Width.**
- `ai_width` is `switch stops + guesses × Σ_slots 2^(sites of slot)` (pre-merge combinations
  actually enumerated). It is checked ≤ `WIDTH_CAP`.
- The flat product, `guesses × 2^(Σ sites) × 12 × switch stops`, is reported next to it.

**Loose.** Every `LoadBattlerAbility DEFENDER` read draws its own bit (trainer_ai.c:1191-1198), and
every `IfSpeedCompare*` its own tie bit (battle_lib.c:1405-1445). Slots are enumerated jointly when
the total bit count is ≤ 18, and per slot otherwise. Per slot is exact in loose, because every
decomp read there is an independent draw.

- [ ] **Step 1: Write the tests.**
  - `test_factored_equals_joint_bruteforce`: on Hypothesis states with Kaizo tables and synthetic
    site tables, the factored distribution equals a joint enumeration over all slots' bits and the
    12 tiebreaks, when Σ sites ≤ 14.
  - `test_kaizo_sampled_frequencies_match`: 20 000 `sample_ai_outcome` draws and the policy match
    the distribution (chi-square, p > 1e-3).
  - `test_kaizo_width_under_cap`: `ai_width` ≤ 131072 for each of Roark's six as the active.
  - `test_vanilla_layout_frozen`: the vanilla shapes, `ENUMERATION_WIDTH == 3840`, and Task 2's
    bit-equality fixtures.
  - `test_one_scalar_guess_is_exact_for_roark`: for every species of both games' tables and each
    of Kaizo Roark's six, at most one `LoadBattlerAbility DEFENDER` read per decision can change a
    score. This settles Ruling 6 as data, and the test re-runs it whenever later tasks add reads.
- [ ] **Steps 2-4:** Run the tests and see them fail. Implement. Then run `tests/ai`, `tests/search`
  and the fast tier.
- [ ] **Step 5: Measure.**
  - Measure `ai_rows` µs per state for 1000 vanilla Roark states and 1000 Kaizo Roark states (from
    the save, `tests/kaizo` fixtures).
  - Measure the AI share of one Stage B node expansion on a Kaizo root (`benchmarks/solve_timing.py`
    inputs, depth 1).
  - Record both in the report and in kaizo_roark.md §14.
  - **Stop and report to the user if the AI share of a Kaizo node expansion exceeds 50%** (spec §6).
- [ ] **Step 6:** Mutation evidence. Factor without the shared guess (independent per slot), and
  drop the tie subsets; each must fail. Commit `feat(ai): per-slot Kaizo AI outcome layout`.
